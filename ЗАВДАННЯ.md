## 1. Мета

Завдання перевіряє здатність спроєктувати фінансово-критичну систему, де ціна
помилки — втрата чи дублювання грошей, а не просто некоректний UI-стан.
Очікується **реальна декомпозиція на кілька окремих сервісів**, що спілкуються
асинхронно, зі своїми базами даних, і де узгодженість між ними — предмет
свідомого архітектурного рішення, а не побічний ефект спільної транзакції.

На відміну від попередніх завдань серії, кандидат стартує **не з чистого аркуша**:
частина кодової бази вже написана і надається як стартовий репозиторій (див.
розділ 3). Це навмисно — окрема суттєва навичка, яку тут перевіряємо: вміння
розібратись у чужому коді, зрозуміти його межі та наміри автора, і безпечно
розвивати й виправляти систему, а не переписувати все заново.

**Що перевіряємо:**
- Здатність розібратись у наданій кодовій базі без детального супроводжуючого
  опису кожного файлу — читанням коду, тестів і README
- Проєктування double-entry (подвійного) бухгалтерського обліку з інваріантом
  "сума дебетів = сумі кредитів" на кожній операції
- Event Sourcing як основний спосіб зберігання стану гаманця/рахунку (а не CRUD
  над "поточним балансом")
- CQRS: розділення шляху запису (event store) і шляху читання (проєкції/read-моделі)
- Saga-оркестрацію (хореографічну або оркестровану — на вибір, з обґрунтуванням)
  між реальними окремими сервісами, включно зі стратегією компенсації
- Ідемпотентність на межі системи (idempotency keys для API-запитів) і всередині
  (ідемпотентні обробники подій)
- Наскрізну спостережуваність: розподілена трасировка (OpenTelemetry) одного
  запиту через кілька сервісів і чергу
- Стійкість до часткових відмов: circuit breaker / retry з backoff при виклику
  іншого сервісу, graceful degradation
- Свідоме рішення щодо API-шару для фронтенду (GraphQL gateway/BFF, що агрегує
  дані з кількох сервісів, або альтернатива — з обґрунтуванням)
- Уміння виявляти й безпечно виправляти проблеми в чужому коді, не ламаючи
  наявну функціональність і не переписуючи все без потреби

## 2. Стек технологій

| Шар | Технологія |
|---|---|
| Backend-сервіси | NestJS (TypeScript), **мінімум 3 окремі деплойовані сервіси** (наприклад: `ledger-service`, `payments-service`, `notifications-service`) — не модулі одного застосунку, а окремі процеси/контейнери зі своїми БД |
| API-шар для фронтенду | GraphQL gateway (Apollo Federation / schema stitching) або BFF на NestJS — на вибір, з обґрунтуванням |
| Frontend | Next.js (App Router, TypeScript) |
| База даних | PostgreSQL — окрема схема/інстанс на сервіс (database-per-service) |
| Event Store | Власна реалізація на PostgreSQL (append-only таблиця подій) **або** EventStoreDB — на вибір, з обґрунтуванням |
| Черги / Events | Redis Streams, RabbitMQ або Kafka — на вибір, з обґрунтуванням вибору саме для доменних подій між сервісами |
| Real-time | WebSocket — трансляція зміни балансу/статусу транзакції клієнту |
| Автентифікація | JWT (access + refresh), окремий `auth`-контекст, що не змішаний з доменною логікою ledger |
| Спостережуваність | OpenTelemetry (трасування наскрізь через сервіси й чергу), структуроване логування з кореляційним/trace ID, `/metrics` |
| Контейнеризація | Docker + docker-compose (обов'язково); окремий контейнер на кожен сервіс + брокер + БД |

## 3. Стартовий репозиторій

Кандидат отримує посилання на приватний Git-репозиторій із частково готовим
кодом і працює далі в ньому (форк або окрема гілка) — а не створює проєкт з нуля.

### 3.1 Що вже надано

- Базова монорепо-структура (окремі директорії/пакети під кожен сервіс і
  фронтенд), спільний lint/prettier/tsconfig
- `docker-compose.yml`, що піднімає всі БД, брокер подій і сервіси-заглушки —
  проєкт вже стартує командою `docker-compose up`, хай і з неповною
  функціональністю
- Повністю реалізований модуль автентифікації (реєстрація/логін, JWT access +
  refresh) — усередині `ledger-service`, з тестами, що проходять
- `ledger-service`: працює, покритий частиною тестів, але баланс гаманця
  реалізовано "наївно" — прямим CRUD-оновленням поля `balance`, без event
  sourcing і без явного інваріанта подвійного запису
- `payments-service`: створений як каркас (модулі, контролери, DTO існують),
  але бізнес-логіка переказу як саги — не реалізована, ендпоінти повертають
  заглушки
- `notifications-service`: не реалізований взагалі, є лише порожній Nest-проєкт
  і підключення до брокера подій
- Базовий Next.js-фронтенд: сторінки логіну/реєстрації та список гаманців
  готові й працюють проти наявного API; сторінок переказу, split-рахунків і
  admin-екрана немає
- CI-конфігурація, що запускає лінт і наявні тести на push

### 3.2 Що потрібно знайти й виправити самостійно

У наданому коді свідомо закладено кілька проблем — їх точний перелік і
локації **не розкриваються заздалегідь**, це частина завдання. Орієнтовно
вони належать до таких категорій:

- Проблема узгодженості при конкурентному доступі до одного й того самого
  гаманця (можливість "подвійної витрати" за певних умов одночасних запитів)
- Місце, де вхідні дані не валідуються належним чином і/або де можлива
  авторизаційна діра (користувач потенційно може вплинути на чужий гаманець)
- Тест або два, що заведені як TODO/skip і мають бути доведені до робочого
  стану, або тест, що проходить "випадково" й не насправді перевіряє те, що
  заявлено в назві

Кандидат має самостійно виявити ці місця (через ревʼю коду, написання тесту,
що їх відтворює, або аналіз логів/поведінки), задокументувати кожну знахідку
в README (в чому проблема, як відтворити, як саме виправлено) і виправити.
Немає потреби шукати щось поза цими трьома категоріями — але формулювання
навмисно не точкове, воно теж частина оцінки самостійності.

### 3.3 Основне завдання поверх стартового коду

1. Відрефакторити зберігання балансу в `ledger-service` з наївного CRUD на
   event sourcing + CQRS-проєкцію, зберігаючи існуючі публічні API-контракти
   там, де це розумно, і явно документуючи будь-які breaking changes там, де
   без них не обійтись
2. Реалізувати сагу переказу в `payments-service` на базі наявного каркаса
   (контролери/DTO вже є — бізнес-логіку, взаємодію з `ledger-service` і
   компенсацію потрібно дописати)
3. Реалізувати `notifications-service` з нуля (real-time сповіщення через
   WebSocket, стрічка активності)
4. Дописати фронтенд: форму переказу з live-статусом, split-рахунки,
   admin-екран — з опорою на вже наявні сторінки логіну/списку гаманців як
   орієнтир по стилю й підходу до Server/Client Components
5. Не ламати наявний зелений CI без пояснення в README, чому конкретна зміна
   була необхідною (наприклад, зміна контракту API через рефакторинг на event
   sourcing — це очікувано і прийнятно, просто має бути описана)

Решта вимог з розділів 4–6 нижче стосується як нового коду, так і того, що
залишається від стартового репозиторію після рефакторингу.

## 4. Суть проєкту: "P2P Ledger" — гаманці, перекази та розщеплені платежі

Спрощений аналог внутрішньої платіжної системи (щось на кшталт ядра Wise/Revolut
у мініатюрі): користувачі мають мультивалютні гаманці, переказують гроші одне
одному, створюють групові рахунки (split bills), а система веде повний та незмінний
журнал операцій, з якого будь-який баланс можна відновити з нуля.

### 4.1 Сервіси (мінімальна декомпозиція)

- **`ledger-service`** — джерело істини. Зберігає потік подій (`MoneyDeposited`,
  `TransferInitiated`, `TransferCompleted`, `TransferFailed`, `HoldPlaced`,
  `HoldReleased` тощо), будує проєкції балансів, гарантує інваріант
  подвійного запису
- **`payments-service`** — оркеструє флоу переказу/split-платежу як сагу,
  звертається до `ledger-service` для резервування й списання коштів,
  керує станом саги, реалізує компенсаційні дії при відмові
- **`notifications-service`** — підписаний на доменні події (через чергу),
  надсилає real-time сповіщення через WebSocket і формує стрічку активності
  користувача
- (опційно, бонус) **`fx-service`** — курси конвертації валют, кешовані з TTL,
  використовуються при міжвалютних переказах

Кожен сервіс має власну БД. Пряме читання одним сервісом бази іншого — заборонено;
взаємодія лише через API або події.

### 4.2 Функціональні вимоги

**Автентифікація та профілі**
- Реєстрація/логін, JWT access + refresh (уже реалізовано в стартовому
  репозиторії — переносити/адаптувати за потреби при рефакторингу ledger-service)
- У кожного користувача — один або кілька гаманців (за валютами: наприклад USD,
  EUR, UAH), гаманець створюється автоматично при першій потребі

**Ledger (подвійний запис)**
- Кожна грошова операція записується як мінімум двома проводками (дебет одного
  рахунку, кредит іншого), сума яких завжди дорівнює нулю в межах однієї операції
- Стан гаманця (баланс) — це **проєкція**, що обчислюється (і кешується/матеріалізується)
  з потоку подій, а не окреме поле, яке довільно оновлюється
- Має існувати ендпоінт/скрипт, що повністю перебудовує баланс з нуля з event-логу
  і звіряє його з матеріалізованою проєкцією (reconciliation)
- Підтримка "холдів" (hold/reserve): кошти можна тимчасово заблокувати (наприклад,
  на час обробки переказу) так, щоб вони не були доступні для витрати, але й не
  були списані остаточно, поки операція не підтверджена

**Перекази (Transfer) як сага**
- Переказ між двома гаманцями (можливо різних валют — з конвертацією за поточним
  курсом) складається з кроків: перевірка ліміту/фроду → holds на рахунку
  відправника → підтвердження → списання + зарахування → сповіщення
- Якщо будь-який крок далі відмовляє (наприклад, отримувач заблокований, курс
  валют застарів, ліміт перевищено) — попередні кроки мають бути коректно
  скомпенсовані (hold знімається, гроші повертаються, стан саги — `Failed`,
  а не "зависає" в невизначеному стані)
- Клієнт може опитати статус переказу (poll) і/або отримати його в реальному часі
  через WebSocket
- **Ідемпотентність:** повторний запит на створення переказу з тим самим
  `Idempotency-Key` не повинен створити другий переказ ні за яких умов
  (включно з одночасними дублюючими запитами — race condition)

**Розщеплені платежі (Split Bill)**
- Користувач створює груповий рахунок: загальна сума, список учасників і частка
  кожного (порівну або кастомна)
- Кожен учасник підтверджує й сплачує свою частку окремим переказом на адресу
  ініціатора; загальний статус рахунку агрегується з часток (Pending → Partially
  Paid → Settled)
- Прострочені (не оплачені вчасно) частки — конфігурована поведінка: нагадування
  через `notifications-service` (подія в черзі)

**Реальний час**
- Клієнт бачить зміну балансу й статусу переказу без перезавантаження сторінки
- При втраті WebSocket-з'єднання — при перепідключенні клієнт має отримати
  актуальний стан (а не покладатись лише на пропущені push-події)

**Адмін/спостережуваність (для перевірки коректності системи, не для кінцевого користувача)**
- Ендпоінт (захищений, для admin-ролі) для перегляду event-логу конкретного
  гаманця в хронологічному порядку
- Ендпоінт reconciliation-звірки: сума всіх дебетів і кредитів у системі за період
  повинна дорівнювати нулю (глобальний інваріант подвійного запису)
- Дашборд-сторінка на фронтенді, що показує кілька останніх трасувань (traces) і
  час обробки саги переказу по кроках (з OpenTelemetry-даних)

**Frontend (Next.js)**
- Логін/реєстрація, список гаманців з балансами по валютах — уже реалізовано в
  стартовому репозиторії; початкове завантаження балансів через Server
  Component, подальші оновлення — вже по WebSocket на клієнті
- Форма переказу та все, що працює з live-статусом (Client Component з
  WebSocket-з'єднанням): одержувач за email/username, сума, валюта, live-статус
  виконання переказу (кроки саги — можна показати як прогрес)
- Мутації, що не потребують реального часу (створення split-рахунку, підтвердження
  профілю тощо), варто робити через Server Actions; мутації, чутливі до
  ідемпотентності (сам переказ), — через API з явним `Idempotency-Key`, а не
  напряму через Server Action, щоб керувати заголовком і повторними спробами
  на клієнті
- Створення й перегляд split-рахунків, оплата власної частки
- Стрічка активності (real-time), фільтр за типом операції
- Admin-екран: перегляд event-логу гаманця, статус reconciliation, базовий
  трейс-переглядач останніх операцій
- Стани loading/empty/error (включно зі Suspense-стрімінгом важких секцій
  дашборду), offline/reconnect-індикатор для WebSocket
- README має коротко пояснювати, за яким принципом кандидат провів межу
  Server/Client Components у новому коді та чи змінював підхід наявних сторінок

### 4.3 Нефункціональні вимоги

- Кожен сервіс — окремий деплойований юніт зі своєю БД; заборонено спільне
  пряме читання чужої БД
- Транзакційна межа кожного окремого сервісу — стандартна БД-транзакція;
  узгодженість **між** сервісами — лише через сагу й асинхронні події,
  ніяких розподілених XA-транзакцій
- Явна стратегія обробки "застряглих" саг: таймаут кроку саги і автоматична
  компенсація/ретрай з обмеженою кількістю спроб
- Ідемпотентність: idempotency keys на вхідних мутуючих ендпоінтах
  (`POST /transfers` тощо) і ідемпотентні консюмери подій (дедуплікація за
  event ID)
- Circuit breaker (або еквівалент) на викликах `payments-service` →
  `ledger-service`: при недоступності ledger — payments не повинен "зависати"
  назавжди чи губити запит, а коректно позначати операцію як таку, що потребує
  повтору
- Розподілена трасировка: один trace ID проходить через весь ланцюжок
  HTTP-виклик → подія в черзі → обробка в іншому сервісі; видно в
  admin-дашборді або через сумісний бекенд трасування (Jaeger/Zipkin-сумісний
  формат — реалізація локального колектора вітається, але не обов'язкова)
- Валідація вхідних даних на всіх шарах, захист від основних вразливостей
  (ін'єкції, XSS, IDOR — перевірка, що користувач не може побачити/списати
  чужий гаманець)
- Rate limiting на створення переказів і на логін
- Структуроване логування з кореляційним/trace ID у кожному сервісі
- Конфігурація через `.env`, окремі `.env.example` для кожного сервіса
- CI pipeline (GitHub Actions): лінт, типчек, unit- і інтеграційні тести для
  кожного сервіса окремо, запуск на push/PR; наявний CI не повинен зламатись
  без задокументованої причини

## 5. Архітектурні вимоги

- Мінімум 3 окремі деплойовані NestJS-сервіси з власними БД (не модулі одного
  моноліту) + брокер подій + gateway/BFF для фронтенду
- Явна діаграма архітектури в README: сервіси, напрямки викликів (синхронні
  HTTP vs асинхронні події), межі транзакцій, а також що саме з наданого
  стартового коду залишилось як є, а що перероблено
- Явна модель узгодженості для кожного інваріанта системи: що гарантується
  синхронно (в межах одного сервісу), що — асинхронно/eventually (між сервісами),
  і чому саме так
- Явний опис стратегії саги: оркестрована (є явний координатор-сервіс, що веде
  стан саги) чи хореографічна (кожен сервіс реагує на події й публікує свої) —
  з обґрунтуванням вибору для цього домену
- Опис стратегії компенсації для кожного кроку саги переказу: що саме
  відкочується і як, якщо крок N зазнав невдачі
- Схема подій (event schema) з версіонуванням: як система обробляє зміну
  структури події, якщо стара подія вже лежить в event-логі
- Індекси в БД для полів, що використовуються в проєкціях, ідемпотентних
  перевірках (idempotency key, event ID) і перевірках прав доступу

## 6. Тестування

- Unit-тести для ключової бізнес-логіки: побудова проєкції балансу з потоку
  подій, перевірка інваріанта "сума дебетів = сумі кредитів" на кожній операції,
  логіка компенсації саги при відмові на кожному з кроків
- Інтеграційні/e2e тести на критичні флоу:
  - переказ між двома гаманцями (включно з конвертацією валют) → перевірка,
    що обидва баланси й event-лог узгоджені
  - навмисна відмова одного з кроків саги (наприклад, отримувач заблокований
    після резервування коштів) → перевірка коректної компенсації й що кошти
    не "зникли" і не задублювались
  - повторний запит переказу з тим самим idempotency key (включно з
    одночасними паралельними запитами) → перевірка, що переказ створено рівно
    один раз
  - reconciliation-тест: після серії випадкових операцій сума всіх проводок
    у системі дорівнює нулю
- Навантажувальний тест: конкурентні перекази з одного гаманця на суму, що
  перевищує баланс лише за умови одночасного виконання (race condition на
  списанні) — перевірка, що система не допускає "подвійної витрати"
- Тест(и), що відтворюють знайдені в стартовому коді проблеми (розділ 3.2) —
  до виправлення тест червоний, після — зелений; це і є доказ, що проблему
  справді знайдено й усунено, а не просто описано словами в README
- Наявні в стартовому репозиторії тести мають лишитись зеленими (або їх зміна
  явно обґрунтована в README)
- Опційно: тести компонентів на фронтенді, тест reconnect-логіки WebSocket

     як їх виявлено, яким тестом підтверджено, як виправлено

   - опис моделі узгодженості (де сильна, де eventual, і чому)
   - опис стратегії компенсації саги переказу

   - результати навантажувального/race-condition тесту
   - список того, що не встигли зробити або зробили б інакше за наявності

5. Swagger-документація API кожного REST-сервіса та/або GraphQL-схема gateway
6. CI-конфігурація (`.github/workflows/*.yml`) із лінтом і тестами для кожного
   сервіса

## 8. Критерії оцінки

| Критерій | Вага |
|---|---|
| Декомпозиція на сервіси, межі відповідальності, обґрунтованість рішень щодо узгодженості | 15% |
| Робота з наданим стартовим кодом: чи знайдено закладені проблеми, чи безпечно й обґрунтовано зроблено рефакторинг | 15% |
| Коректність double-entry обліку та event sourcing (інваріанти, reconciliation) | 15% |
| Коректність саги переказу: компенсація при відмові, відсутність "застряглих" станів | 15% |
| Ідемпотентність (API-рівень і обробка подій), відсутність race conditions/double-spending | 10% |
| Спостережуваність: наскрізна трасировка, кореляційні ID, метрики | 10% |
| Безпека та валідація (включно з IDOR між гаманцями/сервісами) | 10% |
| Тести, включно з навантажувальним/race-condition тестом | 5% |
| Якість фронтенду та документація/DX | 5% |

## 9. Що НЕ є метою

- Реальна інтеграція з банківськими рейлами, SWIFT, картковими процесингами —
  усе це мок-логіка всередині системи
- Kubernetes / service mesh у продакшн-якості — docker-compose достатньо;
  Helm chart чи k8s-маніфести можуть бути опційним бонусом
- Повноцінна система виявлення шахрайства (fraud detection) на основі ML —
  досить простих детермінованих правил (ліміти, чорні списки)
- Ідеальний дизайн UI
- 100% покриття тестами
- Підтримка десятків валют і складної системи хеджування курсів — досить
  кількох валют і простого кешованого курсу конвертації
- Власна повноцінна реалізація EventStoreDB-подібної СУБД — обрана технологія
  (Postgres append-only чи готовий EventStoreDB) використовується як є
- Переписування наданого стартового коду "з нуля" там, де це не продиктовано
  явною потребою (рефакторинг ledger-service — потрібен; переписування
  auth-модуля чи docker-compose "бо так краще" — ні)
